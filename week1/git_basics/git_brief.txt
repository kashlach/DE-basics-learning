______Компоненты инфраструктуры______
Рабочая директория - рабочая копия нек-рой версии проекта; файлы, с к-рыми работаем
Индекс (staging area, неофиц. кэш-зона) - файл с фиксацией изменений, подготовленных для добавления в коммит
Репозиторий - папка проекта, отслеживаемого Git, содержащая дерево изменений проекта. Файлы истории хранятся в папке .git/ внутри папки проекта

РД -> git add -> Индекс -> git commit -> Репо

   <------------------- remove <---------------------

# git add + git commit = git commit -a (a от all) - "ленивый" коммит
  заменяет две команды одной, но в коммит НЕ ПОПАДУТ файлы в статусе UNTRACKED
  Практический пример: 
  Создали новый файл со стилями css, добавили эти стили в отслеживаемые файлы html и сделали ленивый коммит. 
  Результат - нерабочие файлики, т.к. файл .css не будет добавлен в коммит
  Как починить: т.к. каждый коммит должен фиксировать РАБОЧУЮ ВЕРСИЮ (атомарные изменения), нужно внести изменения в предыдущий коммит, а не делать новый, который будет чинить прошлый. git add + git commit --amend

# git reset
  Сценарии использования:
  1. убираем из индекса все, что сейчас staged for commit (changes to be commited) # git reset = git reset --mixed HEAD
  1.2 убираем из индекса конкретный файл # git reset filename = git reset --mixed filename
    --то есть здесь изменения в файлах сохраняются в рабочей дириктории, только исключаем их из индекса
  2. возврат к состоянию последнего коммита # git reset --hard
    --здесь мы откатываем сами изменения в файлах к состоянию предыдущего коммита, безвозвратно(!)
  3. переход к состоянию нек-рого коммита
    # git reset shorthashcode - к состоянию указанного коммита
	--
    # git reset HEAD~1 = git reset HEAD^ - возврат на один коммит назад
	# git reset HEAD~2 = git reset HEAD^^ - на два коммита от последнего
	--перемещаем указатель HEAD на нужную позицию. Журнал перемещений указателя HEAD можно посмотреть по команде git reflog (напрмиер чтобы найти идентификаторы для отката; это журнал только ЛОКАЛЬНЫХ изменений и история тут хранится не вечно)
	--то есть коммит не удаляется, мы только перемещаем указатель
	--изменения в файлах сохраняются в рабочей директории, меняем состояние репозитория
	--чтобы отменить и изменения в рабочей директории тоже, используем например # git reset HEAD^ --hard
	
Еще раз про ключи:
  soft = затрагивает только репозиторий, изменения из коммита перебросятся в индекс и останутся в рабочей директории
  mixed = сбросим индекс и удалим коммит, но изменения в рабочей папке останутся
    (git reset --mixed HEAD = возврат к коммиту, на к-рый указывает HEAD, с очищением индекса, но сохранением раб. директории)
  hard = удаляет изменения везде (!аккуратно, если изменения не были закоммичены. Если были, то можем восстановить)
  --
  git commit --amend = (git reset --soft HEAD~1 + git commit) = отменяем последний коммит, его изменения помещаем в индекс
  
# git revert 
  сравнение с git reset - упрощенно тут перемещаем указатель Head, удаляя коммиты из истории, то есть меняем историю коммитов 
              git revert - тут историю не трогаем, создаем новый коммит, который отменяет изменения, сделанные в указанном коммите.
			               например коммиты A -> B -> C -> D, делаем git revert C, гит смотрит изменения в C, применяет обратные изменения и создает новый коммит с ними  
			               то есть гит вычисляет "анти-изменения" и накладывает их поверх того, что есть сейчас
			  reset не может удалить коммит из середины истории, оставив изменения более поздних коммитов, а revert дает точечно убрать только ненужные изменения
			  
			  
  Сценарии:
  git revert HEAD/хэш-код - откатим последний/указанный коммит
  git revert HEAD после git revert HEAD - вернем состояние до отката
  git revert --abort - отменим незавершенный откат коммита (статус REVERTING)
  git revert хэш-код1..хэш-код2 - откатим серию коммитов, создадим так же серию новых коммитов для каждого в диапазоне
  
  Ключи:
  --no-edit = без ввода сообщения для коммита
  --no-commit = без создания нового коммита (изменения попадают в индекс)

# git diff - разница между указанными коммитами или указанным и текущим состоянием репозитория
  git diff - вывод изменений после последнего коммита (не добавленных в индекс)
  git diff HEAD вывод изменений после последнего коммита (включая добавленные в индекс)
  git diff --staged = git diff --cached - вывод изменений, добавленных в индекс
  git diff file1 file2 - сравнение произвольных файлов даже вне git-репозитория
  
# git show = git show HEAD - изменения в указанном коммите или в HEAD
  казалось бы, что git diff hash1..hash2 дб = git show hash1..hash2, но нет
  show = последовательное отображение изменений в каждом из коммитов в диапазоне
  diff = суммарное изменение между двумя коммитами

_____История коммитов_____

# git log - история коммитов в текущей ветке
  Ключи:
    --oneline = краткий формат (хэш-код и сообщение)
	--stat = статистика (сколько было файлов в коммите, сколько строк удалено/добавлено и тп)
	--graph = графическое отображение веток
	--pretty=format:"..." = можно задать формат вывода истории с использованием плейсхолдеров типа %as
	--since="yyyy-mm-dd" = история с даты
	--until="yyyy-mm-dd" = история до даты
	
	-p = посмотрим патчи (пакеты изменений(?)) по коммитам
	-4 = ограничим к-во коммитов в выводе истории
	
# git shortlog - краткая история коммитов, сгруппированная по авторам
  -e = добавит почту рядом с именев автора коммита
  -n = отсотирует вывцодм по к-ву коммитов DESC
  -s = только имя и к-во коммитов

_____Как не отслеживать определенные объекты_____
Файл .gitignore определяет шаблоны файлов и директорий, которые Git должен игнорировать и не отслеживать
Его нужно создать, напрмиер nano .gitignore (он будет скрытый, т.е. смотрим через ls -a) и прописать в нем шаблон(ы), по к-рому будут исключаться файлы для отслеживания: 
 *.log - все файлы с расширением log
 logs/* - все содержимое папки logs
 !some_pattern - исключение из исключений
 git add -f filename - игнорируем исключение на отслеживание
 # - комментарий к исключению
 
!Если файл уже находился в отслеживании (коммитился), то правила .gitignore на этот файл не распространяются. Можно удалить файл из стейджда, но оставить на диске git rm --cached <filename>
!!Уже есть готовые наборы типовых исключений
