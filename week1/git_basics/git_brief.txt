______Компоненты инфраструктуры______
Рабочая директория - рабочая копия нек-рой версии проекта; файлы, с к-рыми работаем
Индекс (staging area, неофиц. кэш-зона) - файл с фиксацией изменений, подготовленных для добавления в коммит
Репозиторий - папка проекта, отслеживаемого Git, содержащая дерево изменений проекта. Файлы истории хранятся в папке .git/ внутри папки проекта

РД -> git add -> Индекс -> git commit -> Репо

# git add + git commit = git commit -a (a от all) - "ленивый" коммит
  заменяет две команды одной, но в коммит НЕ ПОПАДУТ файлы в статусе UNTRACKED
  Практический пример: 
  Создали новый файл со стилями css, добавили эти стили в отслеживаемые файлы html и сделали ленивый коммит. 
  Результат - нерабочие файлики, т.к. файл .css не будет добавлен в коммит
  Как починить: т.к. каждый коммит должен фиксировать РАБОЧУЮ ВЕРСИЮ (атомарные изменения), нужно внести изменения в предыдущий коммит, а не делать новый, который будет чинить прошлый. git add + git commit --amend

# git reset
  Сценарии использования:
  1. убираем из индекса все, что сейчас staged for commit (changes to be commited) # git reset = git reset --mixed HEAD
  1.2 убираем из индекса конкретный файл # git reset filename = git reset --mixed filename
    --то есть здесь изменения в файлах сохраняются в рабочей дириктории, только исключаем их из индекса
  2. возврат к состоянию последнего коммита # git reset --hard
    --здесь мы откатываем сами изменения в файлах к состоянию предыдущего коммита, безвозвратно(!)
  3. переход к состоянию нек-рого коммита
    # git reset shorthashcode - к состоянию указанного коммита
	--
    # git reset HEAD~1 = git reset HEAD^ - возврат на один коммит назад
	# git reset HEAD~2 = git reset HEAD^^ - на два коммита от последнего
	--перемещаем указатель HEAD на нужную позицию. Журнал перемещений указателя HEAD можно посмотреть по команде git reflog (напрмиер чтобы найти идентификаторы для отката; это журнал только ЛОКАЛЬНЫХ изменений и история тут хранится не вечно)
	--то есть коммит не удаляется, мы только перемещаем указатель
	--изменения в файлах сохраняются в рабочей директории, меняем состояние репозитория
	--чтобы отменить и изменения в рабочей директории тоже, используем например # git reset HEAD^ --hard
	
Еще раз про ключи:
  soft = затрагивает только репозиторий, изменения из коммита перебросятся в индекс и останутся в рабочей директории
  mixed = сбросим индекс и удалим коммит, но изменения в рабочей папке останутся
    (git reset --mixed HEAD = возврат к коммиту, на к-рый указывает HEAD, с очищением индекса, но сохранением раб. директории)
  hard = удаляет изменения везде (!аккуратно, если изменения не были закоммичены. Если были, то можем восстановить)
  --
  git commit --amend = (git reset --soft HEAD~1 + git commit) = отменяем последний коммит, его изменения помещаем в индекс
  
# git revert 
  сравнение с git reset - упрощенно тут перемещаем указатель Head, удаляя коммиты из истории, то есть меняем историю коммитов 
              git revert - тут историю не трогаем, создаем новый коммит, который отменяет изменения, сделанные в указанном коммите.
			               например коммиты A -> B -> C -> D, делаем git revert C, гит смотрит изменения в C, применяет обратные изменения и создает новый коммит с ними  
			               то есть гит вычисляет "анти-изменения" и накладывает их поверх того, что есть сейчас
			  reset не может удалить коммит из середины истории, оставив изменения более поздних коммитов, а revert дает точечно убрать только ненужные изменения
			  
			  
  Сценарии:
  git revert HEAD/хэш-код - откатим последний/указанный коммит
  git revert HEAD после git revert HEAD - вернем состояние до отката
  git revert --abort - отменим незавершенный откат коммита (статус REVERTING)
  git revert хэш-код1..хэш-код2 - откатим серию коммитов, создадим так же серию новых коммитов для каждого в диапазоне
  
  Ключи:
  --no-edit = без ввода сообщения для коммита
  --no-commit = без создания нового коммита (изменения попадают в индекс)

_____Как не отслеживать определенные объекты_____
Файл .gitignore определяет шаблоны файлов и директорий, которые Git должен игнорировать и не отслеживать
Его нужно создать, напрмиер nano .gitignore (он будет скрытый, т.е. смотрим через ls -a) и прописать в нем шаблон(ы), по к-рому будут исключаться файлы для отслеживания: 
 *.log - все файлы с расширением log
 logs/* - все содержимое папки logs
 !some_pattern - исключение из исключений
 git add -f filename - игнорируем исключение на отслеживание
 # - комментарий к исключению
 
!Если файл уже находился в отслеживании (коммитился), то правила .gitignore на этот файл не распространяются. Можно удалить файл из стейджда, но оставить на диске git rm --cached <filename>
!!Уже есть готовые наборы типовых исключений

# git push - загружаем изменения на удаленный репозиторий

# git pull remote_name - получаем изменения из удал репо и обновляем рабочую копию 
  = git fetch + git merge

# git clone remote_url - создает локальную копию удаленного репозитория, включая всю его историю и ветки
  = mkdir dir_name + git init + git remote add remote_name + git pull
  Команда автоматически:
	 - Создаёт новую папку (с именем репозитория)
	 - Инициализирует в ней git init
	 - Настраивает удалённый репозиторий (git remote add origin)
	 - Скачивает все файлы и всю историю коммитов
	 - Переключается на основную ветку (обычно main или master)

_____Работа с ветками_____
# git branch - смотрим список веток (текущая со *, т.е. это ветка, на которую указывает HEAD)

Виды:
  Main/Master - главная ветка со стабильной версией кода
  Feature - для новых функций
  Bugfix - для исправления ошибок
  Release - для подготовки релиза
  Hotfix - срочные исправления в продакшене
  
# git checkout branchname - переключение на ветку 
  -b - от branch для создания новой ветки (и послед переключения на нее)
  !! это устаревший способ, новый git switch (git checkout перегружена, умеет работать с коммитами и файлами, а switch только для веток)
  
# git switch - переключение на предыдущую ветку, с которой пользователь переключался branchname
  branchname - переключение на ветку branchname
  -c - от create для создания новой ветки (и послед переключения на нее)
  
# git merge branchname - слияние текущей ветки и branchname

# git log branchname - смотрим историю коммитов branchname
# git log --all - история по всем веткам

Пример и шаги для реализации:
  При работе над сайтом нужно реализовать новую функцию, для чего создим новую ветку и будем в ней вести работы. В момент работы в новой ветке обнаружим критическую ошибку, требующую срочного исправления.
  1. Создаем новую ветку feature_branch и переключимся на нее 
     # git checkout -b feature_branch
  2. Работаем в feature_branch и делаем коммиты
  3. Получили сообщение об обнаружении уязвимости => нужна еще одна ветка для hotfix_branch
  4. В feature_branch все изменённые файлы добавить в индекс и сделать коммит (либо припрятать изменения (stash) или добавить их в последний коммит (amend))
  5. Переключаемся на main
     # git checkout main
	 Теперь рабочий каталог имеет точно такой же вид, как перед началом работы над новой функцией (как в момент п.1), то есть Гит вернет к состоянию последнего коммита в переключаемую ветку (тут main)
  6. Создаем новую ветку для реализации исправления и переключимся на нее
     # git checkout -b hotfix_branch
  7. Исправили, закоммитили и хотим включить эти изменения в main
     # git checkout main
     # git merge hotfix_branch
	 Теперь изменения включены в коммит, на который указывает ветка main
	 Тут будет Fast-forward, т.к. коммиты в hotfix_branch - прямые потомки коммита из main, поэтому Гит просто переместит указатель ветки вперёд
  8. Удаляем ветку hotfix_branch, т.к. более она не нужна 
     # git branch -d hotfix_branch
  9. Переключаемся на ветку feature_branch, чтобы продолжить раблту над новой функцией
     # git checkout feature_branch
	 !! Изменения из ветки hotfix_branch не включены в feature_branch. Если их нужно включить, то выполняем git merge main (вливаем ветку main в ветку feature_branch). Но это слияние можно отложить до завершения работы над новой функцией и затем влить ветку feature_branch в main (как в п.7)
 10. Сливаем ветку feature_branch с main
     # git checkout main
     # git merge feature_branch
	 Тут уже не будет Fast-forward, т.к. коммит, на котором мы находимся, не является прямым родителем ветки, с которой мы выполняем слияние.
	 Тут получится "коммит слияния" -  у него более одного предка: последние коммиты объединяемых веток и их общий родительский коммит
 11. Ветку feature_branch можно удалить # git branch -d feature_branch
 

_____Конфликты слияния_____ 
Если изменить одну и ту же часть одного и того же файла по-разному в двух объединяемых ветках, Гит не сможет их объединить. Он остановит процесс до тех пор, пока не разрешатся конфликты
Пример: 
	CONFLICT (content): Merge conflict in filename.ext
	Automatic merge failed; fix conflicts and then commit the result.
	
# git status покажет, какие файлы не объединены (Unmerged paths)

В конфликтующие файлы Гит добавляет спец маркеры конфликтов, чтобы их можно было исправить вручную, пример:
	<<<<<<< HEAD:filename.ext
	<div id="footer">contact : email.support@github.com</div>
	=======
	<div id="footer">
	 please contact us at support@github.com
	</div>
	>>>>>>> feature_branch:filename.ext
		--> до ======= вариант файла в HEAD в main, а после - вариант в feature_branch
		    Можно исправить ручками и сделать git add для каждого файла (добавление файла в индекс означает для Гит, что все конфликты в нём исправлены)
			После можно выполнить git commit для создания коммита слияния
