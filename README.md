## DE-basics-learning

Репозиторий с учебными проектами по направлению Data Engineering. Содержит последовательную серию практических работ - от основ ETL на Python до полноценного пайплайна с Airflow, dbt,Grafana и Superset.

#### О себе
**Текущий опыт**: 3 года PL+ и PL/SQL разработчиком + 9 месяцев в роли аналитика (работа с отчетностью).

**Ключевые навыки из коммерческого опыта**:

- Написание сложных оптимизированных запросов для больших объемов данных (Oracle *преимущественно*, PostgreSQL)
- Разработка хранимых процедур и джобов на PL/SQL
- Построение отчетов в Oracle Repors Builder и MS Report Builder

**Мотивация**: перейти от роли поставщика отчетов, зависимого от смежных отделов, к более независимой позиции аналитика-инженера, способного самостоятельно проектировать систему отчетности.

### Пройденный путь и освоенные навыки
#### Week 1 - Основы etl и работа с данными
**Проект**: pandas_simple_etl

Простейшийи etl-скрипт для анализа продаж из csv. Объединяет данные о продажах с информацией о районах доставки, очищает данные и создает аналитические отчеты.

**Освоено**:

* ETL-пайплайн на Python
* Базовые операции pandas (`read_csv`, `groupby`, `merge`, `agg`)
* Создание виртуального окружения (`venv`) и файла `requirements.txt`
* Работа с Git и GitHub
* Markdown синтаксис для написания документации

**Результат**: аналитические отчеты: продажи по категориям, по районам, топ-продуктов по районам.

#### Week 2 - API → Python → PostgreSQL
**Проект**: github_events_etl

Скрипт для получения 100 последних публичных событий из GitHub Events API, сохранения полученных данных в PostgreSQL - распарсенные поля в одну таблицу, сырой JSON в другую (JSONB), - и выполнения нескольких аналитических запросов.

**Освоено**:

* Запрос к **REST API** (библиотека `requests`, обработка JSON-ответа)
* Запуск **PostgreSQL** в **Docker** (контейнер из образа `postgres:15`, переменные окружения для пользователя/пароля/БД, прокидывание порта)
* Работа с БД из Python (**SQLAlchemy**, `to_sql()`, `text()`)
* Работа с `JSONB` в PostgreSQL (хранение и извлечение данных)
* Выполнение запросов через `docker exec` (запуск SQL-файлов и разовых команд в контейнере для отладки и выгрузки CSV)
* Осмысленное управление зависимостями ( `requirements.in с минимальными версиями → pip freeze > requirements.txt`)

**Результат**: данные GitHub Events в PostgreSQL + CSV-отчеты аналитических запросов.

#### Week 3 - Оркестрация и DWH концепции
##### 3.1 Автоматизация загрузки GitHub Events
**Проект**: autoparse_github_events.py

Периодический сбор данных по GitHub Events API. DAG автоматически запускает парсер каждые 5 минут и логирует запуски в БД.

**Освоено**:

* Контейнеризация с помощью **Docker Compose**
* Взаимодействие с PostgreSQL через `PostgresHook` (метабаза Airflow и целевая БД)
* Разработка **DAG в Airflow** с расписанием
* Использование `PythonOperator`, `BashOperator` и `BranchPythonOperator`
* Обмен данными между задачами через `XCom`
* Использование `Variables` (счетчик запусков)
* Мониторинг выполнения тасков через **Web UI Airflow** и **pgAdmin**

##### 3.2 SCD Type 2 реализация
**Проекты**: source_dag.py, staging_dag.py, scd2_dag.py

Инкрементальная загрузка данных из источника (таблица Customers) в staging-слой и сохранение полной истории изменений атрибутов клиентов (SCD Type 2).

**Освоено**:

- Работа с `XCom` для передачи данных между разными DAG'ами
- Логирование через библиотеку `logging`
- **DWH концепции**: SCD Type 2, Staging-слой, Dimension-слой
- **ELT-подход**
- `MERGE`-операции в PostgreSQL

****Архитектура**:

- **Source** - имитация микросервиса с данными о клиентах
- **Staging** - промежуточный слой для сырых данных (маркировка операций: I/U/D)
- **Dimension** - слой с SCD Type 2 историей (суррогатные ключи, флаг is_active)

#### Итоговый проект - Комплексный ELT-пайплайн
**Проект**: currency-rate-project

Полноценный пайплайн для сбора, трансформации и визуализации данных о курсах валют ЦБ РФ.

**Схема работы**:

```text
API ЦБ РФ → Airflow DAG → PostgreSQL (raw, JSONB) → dbt (staging → intermediate → marts) → Grafana и Superset дашборды + Excel-отчеты + Email-алерты
```

**Освоено**:

- `uv` - менеджер пакетов (как замена `pip` и `venv`)
- `ruff` - форматирование Python-кода
- `pytest` - тестирование Python-кода
- **Dockerfile** - создание образа Airflow с dbt
- **dbt** - трансформация данных в хранилище (модели, тесты, документация)
- **Grafana** - визуализация данных и настройка алертов
- **Superset** - визуализация данных
- Excel-отчетность - еженедельные отчеты, автоматическая отправка на почту
- Мониторинг ETL - дашборд Healthcheck на основе метабазы Airflow

**Ключевые компоненты**:

- dbt-модели (три слоя):
  - Staging: очистка и подготовка сырых данных
  - Intermediate: агрегации и джойны
  - Marts: готовые витрины для дашбордов
- Grafana дашборды:
  - Бизнес-дашборды: курсы валют (USD, THB и общий)
  - Технический дашборд: ETL Healthcheck с алертом при простое >24 часов
- Superset дашборд для анализа качества данных в БД
- Отчетность:
  - Еженедельный Excel-отчет (автоматически по понедельникам, отправка на почту)
  - Сводный отчет через Power Query
  - Алерт по USD при изменении >2% за сутки
- Тесты:
  - API-клиент: проверка URL и формата даты
  - Загрузчик: проверка upsert-логики

### Итоги

За время работы над проектами пройден путь от написания простых ETL-скриптов до создания комплексного ELT-пайплайна с оркестрацией, трансформацией, визуализацией и мониторингом. Освоена база современного стека Data Engineer, что позволяет приблизиться к роли специалиста, который не просто строит отчеты, а может самостоятельно проектировать и реализовывать законченные отчетные комплексы так, чтобы:

- данные были *качественными* (тесты, мониторинг)
- отчеты были *понятными* (интерактивные дашборды, документация)
- процесс был *автоматизированным* (рассылки, самообслуживание)

**Ключевой результат**: сформировано понимание архитектуры современных data-платформ и получены навыки работы с инструментами DE и BI - Airflow, dbt, Docker, PostgreSQL, Grafana, Superset.

#### Что дальше? Зоны роста по пунктам

1. Качество данных
-  нет дашборда, который показывает "здоровье" данных: % заполненных полей, кол-во пропусков, лаг от источника и т.п. Чтобы было видно, что данным можно доверять

2. Прозрачность отчетности
- сейчас дашборды статичны, нет возможности кликнуть на точку графика/метрику и увидеть детальные данные за день/расчет.
- пользователи не могут сами добавить новый фильтр или сохранить свою версию дашборда. Код зашит в provisioning и нет возможности править его в UI.
- нет раздела с ответами на частые вопросы ("почему за сегодня нет данных?", "в какое время обновляются данные?")
- нет механизма, где можно оставить комментарий о том, что график непонятен/неудобен и т.п.

3. Автоматизация
- нет возможности настроить разные фильтры для разных получателей
- пользователи не могут сами настроить, по каким метрикам и с какой периодичностью получать уведомления, все зашито в коде
- нельзя сделать экспорт данных например excel по кнопке прямо из интерфейса (можно настроить через плагины)
